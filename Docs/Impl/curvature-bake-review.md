# 曲率マップベイクロジック レビュー

レビュー日: 2026-09-25  
対象: `8b6b364` 時点の `Editor/Core/`、`Editor/Shaders/FastCurvatureBake.compute`、設定 UI、既存設計書。レビュー開始時に作業ツリーの変更なし。

## 結論と確認範囲

3D 表面サンプルを面積で重み付けして積分し、ハードエッジを別の幅で評価する構成は妥当。UV の密度に直接依存する差分より扱いやすく、全サブメッシュを共通サンプリングすることでマテリアル境界にも対応している。一方、優先して改善したいのは **UV ラスタライズの競合、Geometry モードの法線依存、ラスタライズの仕事量の偏り**。その後に後処理の島間混合、GPU 同期待ち、メモリ使用量を改善する。

本レビューはコードの静的確認と式・バッファサイズの算術確認による。Unity 上のベイク、GPU プロファイリング、画像比較、シェーダーコンパイルは実施していない。性能改善率や実機での再現頻度は未測定。以下の再現条件・検証案は、今後の実装評価用であり実行済みテストではない。実装の変更は本レビューに含まない。

優先度は P1 = 出力の正しさ・実行安定性に関わるもの、P2 = 条件付きの品質問題・性能改善、P3 = 追加改善とする。

## 品質・正しさ

### Q1: G-buffer の所有者が未定義

根拠: `FastCurvatureBake.compute:171` (`WriteTexel`)、`:205` (`RasterInterior`)、`:239` (`RasterConservative`)。

- 内部パスは三角形ごとのスレッドが同じ画素に無条件で書く。重複 UV に加え、境界判定の許容値 `-1e-5` によって共有辺付近も複数の三角形に含まれ得る。
- 保守パスの「空なら書く」は読み取りと書き込みが別であり、複数スレッドが同時に空と判断できる。重複 UV がなくても、隣接する島の拡張領域が交わると発生する。
- 位置・パッチと法線は別バッファへの書き込みで、同じ三角形から来た組として確定する保証がない。単なる「どちらかの三角形が勝つ」より悪い結果になり得る。

改善案: 所有者決定と属性書き込みを分離する。内部パスは整数の三角形 ID などで決定的な所有者を選び、保守パスは内部所有者を保持したうえで距離と ID による優先順位を決める。最後に 1 画素 1 スレッドで所有者の属性を書く。所有者に atomic 操作を入れるだけで、同じパス中に属性も書く方式では組の整合性を保証しにくい。タイル化する場合はタイル内の画素担当スレッドが候補を選ぶ構造も有効。

検証案: 異なる位置・法線・曲率を持つ重複 UV と、1px 未満の隙間のある島を繰り返しベイクする。PNG 化前の G-buffer の所有者・位置・法線の整合性と、繰り返し差分を確認する。

### Q2: Geometry は現在「位置のみ」の推定ではない

根拠: `CurvatureBakeSettings.cs:13` の説明、`FastCurvatureBake.compute:308–365`。

Geometry も描画法線による facing 重みと `nAvg = normalize(sumN)` を使い、さらに法線分割から作ったパッチでサンプルを除外する。計算式は `-8 * dot(nAvg, weightedMean(q-p)) / Radius`。描画法線を変更するだけで値が変わる。

例えば z=0 の平面上で、境界によって重み付き平均変位が `(0.2r, 0, 0)` に偏り、一定のカスタム法線が `(0.5, 0, sqrt(3)/2)` なら、Geometry の出力は Strength=1 で `-8 * 0.5 * 0.2 = -0.8`。平面でも強い凹として扱う。この例は式への代入であり、Unity 実測ではない。同じ一定法線なら facing による相対重みの変化も不要な反例となる。

改善案: Geometry 用の法線・近傍選択を描画法線から分離する。面法線を向きの基準にし、位置群から局所平面や二次曲面を近似する方式を比較する。ただし面法線へ差し替えるだけでは三角形境界で不連続になる可能性がある。境界では接線方向への重心の偏りと真の法線方向変位を分離し、支持点不足も検出する。現在の挙動を維持する場合も、まず「位置のみ」「法線に依存しない」という説明を修正する。

検証案: 同一の平面・球・円柱に通常法線と傾けたカスタム法線を与え、内部と開いた境界を比較する。球での厳密性は連続・対称な支持領域などを前提とし、有限サンプル、法線棄却、境界切断まで含む保証として扱わない。

### Q3: Downsample / Blur / Dilate に島の区別がない

根拠: `FastCurvatureBake.compute:434`、`:461`、`:501`。後処理データは `(value, coverage)` のみ。

Downsample の同じ 2×2 ブロックに別の島が入れば値が平均される。Blur は隣接する有効画素を島に関係なく平均する。Dilate は異なる島の拡張が接触すると混合値を生成する。特に正負の曲率が隣接すると相殺される。3D で評価していても、最終画像のシーム品質までは保証されない。

改善案: UV チャート ID を後処理まで保持し、Blur は同じ島だけに限定する。Dilate は距離と所有者を伝播し、近い島の境界値をコピーする方式を比較する。Downsample は複数島を 1 画素に格納できないため、支配的な島の選択規則と、解像度・UV パディング不足の扱いを定義する。coverage は現状「有効かどうか」の値であり、真の面積カバレッジとして使うなら保守パスの拡張分と区別する必要がある。

検証案: +1 と -1 の島を 0〜4px の間隔で配置し、SSAA、Blur、Dilation を個別に切り替えて境界断面を比較する。

### Q4: 大域的なパッチ ID と局所的な面の隣接は一致しない

根拠: `SurfaceMesh.cs:158–220`、`FastCurvatureBake.compute:335–341`、`:367–405`。

- 途中で終わるハードエッジは、端を回る経路で両側が同じパッチになり、スムース項が対岸も拾う。この制約は `design.md` 第8節に記載済み。
- 同じ連結成分・同じパッチの折り返した面は、表面上で遠くても 3D 距離が Radius 未満なら候補になる。法線が似ていれば facing でも除外されない。
- EdgeCurvature は component と法線の向きだけを確認する。同じ component 内の別の近接面が同じ方向を向く場合、「そのエッジに接する面」以外にもエッジが転写され得る。
- 位置の完全一致による溶接は、意図せず一点で接触した別パーツも結合し得る。一方、微小にずれたシームは結合できない。元位置が同じでも別のボーンウェイトを持つ頂点は、ポーズ後に離れる場合がある。

改善案: 三角形隣接を保持し、局所的にハードエッジを越えない範囲へ近傍を制限する。エッジには隣接面の識別情報も持たせる。単なるパッチ ID の追加だけでは、端を回れるケースは解決しない。溶接は許容誤差だけを増やさず、辺の共有、変形属性、必要に応じた利用者の選択も考慮する。

検証案: 途中で終わる折れ目、U 字に折った薄板、近接した同方向の面、一点接触パーツを使用し、Radius と EdgeWidth の独立性を確認する。

### Q5: 面積保存だけではサンプルの空間的な支持を保証できない

根拠: `SurfaceSampler.cs:39–49`、`:62–98`、`:122–125`。

サンプル数は面積だけで決まり、k=1 は重心に配置する。長さが Radius より十分長くても、幅が極端に狭い三角形はサンプルが 1 個になり、端付近に支持点がなくなる。全体予算によって spacing が広がっても Radius は固定なので、大きな面積を持つメッシュでは局所的な無支持・低支持領域が増える。`sumW == 0` は 0 を返すため、本当に平坦な場所と推定不能な場所を区別できない。

改善案: アスペクト比や最大辺長を考慮した三角形の仮想分割、層化サンプルを比較する。予算不足時はサンプル数・重みの分散・支持距離から信頼度を計算し、低信頼画素だけ追加評価する。面積重みは維持する。単に Quality を上げるだけでは予算到達後の解決にならない。

検証案: 同じ曲面を均等三角形と細長い三角形で作り、メッシュ分割依存性を比較する。出力と併せて支持点数・信頼度画像を確認する。

### Q6: NormalRejection の上端で全候補が棄却される

根拠: `CurvatureBakeSettings.cs:96`、UI `FastCurvatureBakerWindow.cs:139–141`、`FastCurvatureBake.compute:343`。

設定は 1 まで許可するが、`smoothstep(1, 1.25, dot)` は正規化法線の内積が 1 以下なら 0。浮動小数誤差を除けばスムース項が全て消える。0.75 より上ではフェードの終点が 1 を超え、完全に同じ向きでも重み 1 に到達しない。

改善案: 現行の 0.25 幅を維持するなら上限を 0.75 にする。1 までの設定が必要なら終点・端点の意味を再定義し、完全一致を残すのか全棄却するのか明示する。

検証案: 0.75、0.99、1.0 で球のスムース項を比較する。EdgeStrength=0 として現象を分離する。

## 計算効率・実行安定性

### E1: ラスタライズを画素またはタイル単位に分割する

根拠: `FastCurvatureBake.compute:205–275`、`CurvatureGpu.cs:113–124`。

1 スレッドが三角形の UV AABB 全体を二重ループする。大きな三角形では 1 スレッドに数百万回規模の反復が集中し、細長い対角三角形では非被覆領域の走査も多い。保守パスも AABB を再走査する。実際の仕事量は占有画素数ではなく **Σ AABB 内画素数** に近い。三角形数で Dispatch を分割しても 1 三角形の仕事量は制限できず、曲率評価用の適応チャンクもこのパスには適用されない。

改善案: 三角形を UV タイルへ割り当て、タイルごとに画素を並列評価する。あるいは通常の描画による G-buffer 作成と境界補完を比較する。いずれも Q1 の所有者規則を同時に設計する。大三角形だけをタイル分割する段階的変更も可能。

検証案: UV 全域を占める 2 三角形の平面、細長い対角三角形、多数の小三角形で、ラスタライズ時間を別計測する。高速化率や GPU タイムアウトの発生は実機で判断する。

### E2: 非同期メソッド内の同期待ちを減らす

根拠: `CurvatureGpu.cs:249–293`、`:188–195`、`CurvatureBakePipeline.cs:171–190`。

評価チャンクごとに `WaitForCompletion()` で CPU が待ち、その後にのみ `Task.Yield()` する。最終読み戻しも `GetData` で同期する。サンプル生成・ハッシュ構築は同期処理で、途中のキャンセル確認がない。Blur / Dilate も全パスを投入してから読み戻す。非同期 API の形でも、処理中の応答性は限定される。

適応チャンクは前回の所要時間から次回サイズを決めるため、空の UV 領域から密な領域に入る場面で負荷を過小評価し得る。150ms は目標であり上限保証ではない。

改善案: 読み戻し完了を非同期に待ち、未完了の GPU 作業数に上限を設ける。CPU の純粋な配列処理は、Unity オブジェクトの読み取りを済ませてからワーカーへ移すことを検討する。サンプル生成・グリッド構築・後処理の区切りにもキャンセル確認を追加する。キャンセル中も GPU が参照するバッファの寿命を保証する。チャンクは密度の変化に備えた上限も設ける。

検証案: 総時間に加え、メインスレッドの最長占有時間とキャンセル要求から停止までの時間を計測する。

### E3: メモリ予算を総量で管理する

根拠: `CurvatureGpu.cs:101–103`、`SurfaceSampler.cs:39`、`HardEdgeSegments.cs:42–48`。

内部 4096² の GPosition(16B) + GNormal(4B) + result(8B) だけで **448 MiB**。最大 2²² サンプルの GPU 配列は 128 MiB、同数バケットは 32 MiB で、合計 **608 MiB**。これはメッシュ、エッジ、CPU 側の元配列・整列配列・作業配列、出力保存用データを含まない。G-buffer は後処理前に解放されるため、全ステージのバッファを単純に足してピーク値とはしない。

サンプルの budget は `max(MaxSamples, triangleCount)` なので三角形数が多ければ公称上限を超える。エッジも少なくとも 1 セグメントずつ必要なため、入力エッジ数が MaxSegments を超えれば抑制できない。上限に近いエッジ数では segmentLength とセルサイズが大きくなり、近傍候補数も増え得る。

改善案: CPU/GPU 別の見積もりを準備段階で計算し、許容メモリに応じて UV タイル処理・バッファ再利用・品質調整を選ぶ。三角形数そのものが予算を超える場合は、面積保存を伴うサンプル統合などを別途設計する。タイル境界では Blur / Dilate に必要な余白を確保する。

検証案: 2048+SSAA、4096、サンプル・エッジ上限に近い入力について CPU/GPU のピーク使用量を個別計測する。

### E4: ハッシュ探索と無効な項の計算を削減する

根拠: `FastCurvatureBake.compute:147–158`、`:308–365`、`:425–426`、`SpatialHashGrid.cs:24`、`CurvatureBakePipeline.cs:171–185`。

- NeighbourBucket は各セルについて前のセルのハッシュを再計算し、重複がない場合は 1 近傍探索あたり `0+…+26 = 351` 回の比較となる。スムース項・エッジ項でそれぞれ行う。重複防止自体は必要であり、単に外してはいけない。
- バケット衝突で遠いセルの候補も走査する。距離で除外され、重複バケットも除外されるため、現行実装で衝突を直ちに曲率の誤りとは判断しない。
- Strength=0 でも CPU は表面サンプルとグリッドを作る。シェーダーにもスムース項を明示的に省略する分岐がない。Source に応じた集計の省略も記述されていない。GPU コンパイラがどこまで削減するかは未確認。

改善案: 同じセルの近傍バケット一覧の共有・事前計算、セル座標をキーにした占有セル表、候補のセル AABB と検索球の交差判定を比較する。ローカル配列への変更はレジスタ使用量が増える可能性もあるため、現行の再計算方式と実測比較する。低リスクな変更として、Strength=0 のときの CPU/GPU スムース項の省略、両項がゼロの場合の早期経路を追加する。面上で概ね均一な密度なら近傍数は SamplesPerRadius の二乗に比例するため、Standard(6) から Ultra(12) で評価負荷が約4倍になる目安も表示できる。ただし予算制限・メッシュ密度で変わる。

検証案: 探索バケット数、候補数、実際に採用したサンプル数を測り、密度・衝突・ハッシュ計算のどれが支配的かを確認する。

## P3 の追加改善

- **座標精度**: world 座標の float3 を保存し、GPU で近い点同士を減算する。原点から遠い配置では小さい Radius に対して精度が不足し得る。レンダラー付近を原点とした平行移動後の座標で評価し、配置距離を変えて結果が一致するか確認する。
- **CPU 前処理**: CountSamples の予算調整で三角形面積を最大複数回再計算する。面積配列を一度計算して再利用する。品質を変えて再ベイクする場合のトポロジ・ポーズ・設定ごとのキャッシュは、無効化条件を定義してから導入する。
- **後処理の帯域**: Dilate は半径 D に対して全画像を D 回走査する。E3 のタイル化や、境界画素中心の処理、距離伝播方式を比較する。高速な距離伝播に置き換えると現行の平均値による拡張とは見た目が変わるため、品質を同時に評価する。
- **保存精度**: RGB24 PNG は曲率を 8bit に量子化する。線形・非圧縮インポートの設定は適切だが、微弱な曲率の段差が問題になる用途には高精度出力を選択可能にする。全用途で変更する必要はない。

## 改善の進め方と受け入れ確認

1. Q1 の決定的な所有者選択と E1 のタイル化を設計し、繰り返し再現性と大三角形の処理時間を確認する。
2. Q2 の Geometry の意味を確定する。平面をゼロ基準、球・円柱を曲率基準として、境界・カスタム法線・解像度の変化を比較する。
3. Q3 の UV 島を区別する後処理、Q6 の設定端点を修正する。
4. E2・E3 を計測しながら改善し、総時間、UI 応答時間、ピークメモリを別々に評価する。
5. Q4・Q5 の局所近傍・サンプル品質改善を進める。E4 は計測した支配要因に応じて採用する。

比較時はメッシュ、ポーズ、GPU/API、出力解像度、SSAA、Radius、EdgeWidth、Quality を固定して記録する。PNG では飽和や8bit量子化が誤差を隠すため、評価値の段階で符号、平均誤差、最大誤差、繰り返し差分を確認する。性能は CPU 準備、ラスタライズ、曲率評価、後処理、読み戻し・保存を分け、初回と再実行を区別する。現時点では Substance Painter 相当の品質・速度に達しているかは判断できない。

## 既存設計書で更新したい説明

- 「重複 UV は後から書いた三角形」: 並列書き込みのため決定的な順序・属性の整合性を保証していない。
- 「ラスタライズは Σ 占有テクセル数」: 現行ループは Σ AABB 内テクセル数が基準。
- 「Geometry は法線に依存しない」: Q2 のとおり現行実装とは一致しない。
- 「サンプル・セグメントの上限」: 入力三角形数・エッジ数が上限を超える例外を記載する。
- 「UV シームの影響を原理的に受けない」: 3D 評価の利点として限定し、ラスタライズ・後処理・パディングの条件を併記する。
- G-buffer の w は component+1 ではなく patchId+1。ハッシュ重複除外も現在は訪問済み配列ではなく再計算方式。

本書のコード参照は `Editor/Core/` または `Editor/Shaders/` を起点とするレビュー時の行番号。
